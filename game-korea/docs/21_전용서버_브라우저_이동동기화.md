# 전용 서버와 브라우저 이동 동기화

2026-10-21 후속 작업에서 기본 진입점을 본편 도시로 연결했다. 현재 실행 범위와 방법은
[도시 멀티플레이 연결](22_도시_멀티플레이_연결.md)을 따른다. 아래 연습장 기록은 이전 단계의 이력이다.

## 구현 범위

본편과 분리한 2.5D 연습장에서 2~4명이 걷고 달린다. Godot 전용 서버가
연습장용 고정 틱 이동을 실행하고, 브라우저는 내 입력을 예측하고 상대 위치를 보간한다.
기존 싱글플레이 주소와 도시 서비스는 그대로 사용한다.
차량·전투·경찰·NPC·미션·저장 동기화, 공개 서비스 배포는 아직 연결하지 않았다.

## 실행

프로젝트 폴더 `/Users/itaegjin/study/game-korea`에서 빌드한다.

```sh
godot --headless --path . --import
godot --headless --path . --export-release Web output/web/index.html
```

터미널 1 — 로컬 전용 서버:

```sh
godot --headless --path . res://scenes/session/server.tscn
```

터미널 2 — 웹 파일 서버:

```sh
python3 tools/serve_web.py
```

브라우저 탭 두 개에서 같은 주소를 연다:

- http://localhost:8060/?multiplayer=1
- 두 번째 탭도 같은 주소. 탭마다 별도 참가자 ID를 받는다.
- WASD/방향키 이동, Shift 달리기. 각 탭의 `나 P번호`와 좌표 목록으로 확인한다.
- 일반 싱글플레이: http://localhost:8060/
- 성능 로그: http://localhost:8060/?multiplayer=1&perf=1
- 종료: 실행한 두 터미널에서 Ctrl+C. 연결 종료 화면에서는 새로고침으로 새 참가자로 입장한다.

네이티브 클라이언트도 같은 프로토콜을 사용한다:

```sh
godot --path . res://scenes/session/client.tscn -- --server-url=ws://127.0.0.1:9080
```

서버 포트는 `-- --port=숫자`로 바꿀 수 있다. 웹 클라이언트의 기본 서버 주소는
웹 페이지와 같은 호스트의 9080번이다. 현재 기본 서버는 127.0.0.1에만 바인딩하므로
다른 컴퓨터에서 접속하는 공개 멀티 서비스는 아니다. HTTPS 페이지는 WSS가 필요하며,
외부 공개 시 인증·방 생성·TLS·접속 제한을 추가해야 한다.

## 통신과 권한

- `WebSocketMultiplayerPeer` + 동일 RPC 노드 경로 `/root/NetworkSession`.
- 서버 이동 60Hz, 클라이언트 입력 기록 60Hz/묶음 전송 30Hz, 전체 상태 15Hz, 웹 표시 30FPS.
- 서버가 입장 순서대로 참가자 ID를 부여한다. peer ID와 참가자 ID는 별개다.
- RPC의 실제 송신 peer로 소유자를 찾는다. 클라이언트 좌표·속도·대상 ID는 받지 않는다.
- 지속 입력은 틱별 순번·월드 방향·달리기 여부만 포함한다. 묶음 전체의 순번·형식·NaN/Inf·송신자를 검사하고 방향 크기를 1로 제한한다.
  묶음은 최대 8틱, 서버 대기는 최대 120틱이며 한 서버 틱에 입력 하나만 실행한다.
  이전 단일 입력 RPC도 남아 있지만 12ms보다 잦은 입력을 버리고 서버 속도를 초과할 수 없다.
- 입력이 500ms 끊기면 정지한다. 포커스를 잃거나 숨긴 탭에서는 중립 입력을 보낸다.
- 최초 전체 상태를 받은 뒤 입력을 활성화한다. 상태에는 참가자·연결 ID, 위치,
  속도, 바라보는 방향, 걸음 박자, 마지막으로 실행한 입력 순번이 들어간다. 퇴장·늦은 입장도 전체 상태로 반영한다.
- 클라이언트가 3초 동안 서버 상태를 받지 못하면 연결 종료·노드 정리·입력 정지.
- 퇴장한 ID는 같은 방에서 재사용하지 않는다. 새로고침은 새 참가자다.
- TCP의 신뢰 전송을 사용한다. 송신 버퍼가 일정 크기를 넘으면 새 상태/입력을
  추가하지 않는다. TCP 재전송 자체의 지연을 없애지는 않는다.

## 코드

- `scripts/session/session_bootstrap.gd`: 서버/클라이언트 연결, RPC, 입력 만료, 참가자 수명.
- `scripts/session/session_view.gd`: 정적 연습장 바닥, 참가자 이름표와 표시 좌표 UI.
- `scripts/session/session_motion.gd`: 서버·예측 공통 60Hz 이동식, 상대 상태 보간 버퍼.
- `scenes/session/server.tscn`, `client.tscn`: 같은 RPC 경로의 별도 역할 진입점.
- `scripts/core/web_runtime.gd`, `scripts/ui/title_screen.gd`: `multiplayer=1` 웹 주소 분기.
- `tests/session_network_test.gd/.tscn`: 격리한 MultiplayerAPI로 실제 WebSocket 연결 검증.
- `tests/session_context_test.gd`: 역할 초기화 검사는 `auto_connect=false`로 통신 없이 실행.

새 함정: Node의 `_input(InputEvent)`는 엔진 콜백이므로 RPC 이름으로 사용하지 않는다.
또한 타이틀 UI를 만든 뒤 autoload에서 장면을 바꾸면 지연된 `grab_focus`가
트리에서 빠진 컨트롤에 실행될 수 있다. 웹 멀티 분기는 타이틀 UI 생성 전에 한다.

## 입력 예측·위치 보간 (2026-10-21)

- 내 캐릭터: 서버 응답을 기다리지 않고 매 물리 틱 입력을 실행한다. 서버 스냅숏의
  실행 순번까지 입력 기록을 지우고 남은 입력을 재실행해 예측 위치를 복원한다.
- 위치 오차는 표시 좌표에서 지수 감쇠(계수 18/초)로 줄인다. 0.5px 미만은 정리하고,
  80px를 넘는 보정은 즉시 적용한다. 표시 오프셋은 다음 틱 시뮬레이션에 넣지 않는다.
- 상대 캐릭터: 서버 틱 기준 약 100ms 뒤를 표시한다. 수신 기록 사이에서 위치·속도·
  걸음 박자를 선형 보간하고, 방향은 최단 각도로 보간한다. 표시 시간은 뒤로 가지 않는다.
  새 상태가 없으면 마지막 위치에서 멈춘다. 무제한 외삽은 하지 않는다.
- 입력 기록은 최대 120틱, 상대 상태는 최대 32개다. 전송 버퍼가 밀리면 예측도
  상한에서 멈추므로 메모리와 재실행 비용이 계속 늘지 않는다. 연결 종료 시 기록을 지운다.
- 서버와 브라우저 모두 `session_motion.gd`의 고정 1/60초 이동·속도·경계 제한을 쓴다.
  이 경로는 장애물이 없는 별도 연습장 전용이다. 본편 Player의 벽 충돌·피격·층 전환·
  차량 물리 예측으로 확장한 것은 아니다. 입력의 이동량·시간·좌표를 클라이언트에서 받지 않는다.
- 프로토콜에 입력 묶음과 실행 확인 순번이 추가되어 서버와 웹 빌드를 함께 갱신해야 한다.
  예전 웹 탭은 새로고침해 다시 입장한다.
