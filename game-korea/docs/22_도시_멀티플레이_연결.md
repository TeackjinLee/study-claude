# 본편 도시 맵의 멀티플레이 연결

## 현재 범위

기존 본편 `City`의 같은 지도·건물·강·다리·통제 구역 위에 2~4명의 도보 플레이어를 연결한다.
기본 진입 주소 `http://localhost:8060/?multiplayer=1`은 이제 도시 모드다.
싱글플레이의 Main을 여러 번 켜지 않고, 서버와 브라우저의 도시용 세션을 따로 만든다.

- 서버: 도시 배치·정적 충돌·플레이어 입력 실행·참가자 ID·열린 장을 결정한다.
- 브라우저: 같은 배치·예측용 정적 충돌·2.5D 그림·자기 플레이어 추적 카메라·이름표를 만든다.
- 내 입력 예측·서버 실행 순번 확인·미확인 입력 재실행·상대 위치 보간은 이전 구현을 유지한다.
- 건물·강·통제 구역·지도 외곽과 고가 난간의 정적 충돌은 공통 이동 검사로 처리한다.
- 고가도로 층을 스냅숏에 포함한다. 층이 바뀌면 다른 높이 사이를 보간하지 않고 즉시 반영한다.
- 장은 서버 시작 때 고정하며, 시각은 야간 21시로 고정한다. 늦은 입장도 같은 장을 받는다.

차량·보행자·경찰·전투·픽업·미션·개인 저장·공동 진행은 이 경로에서 생성하지 않는다.
도시에 접속해 함께 걷고 달릴 수 있는 단계이며, 본편의 모든 게임 시스템을 공유하는 단계는 아니다.

## 실행

프로젝트 폴더에서:

```sh
godot --headless --path . --import
godot --headless --path . --export-release Web output/web/index.html
```

터미널 1:

```sh
godot --headless --path . res://scenes/session/server.tscn
```

터미널 2:

```sh
python3 tools/serve_web.py
```

브라우저 두 개에서 `http://localhost:8060/?multiplayer=1`을 연다.
방향키/WASD 이동, Shift 달리기. 각 화면의 `나 P번호`가 자기 플레이어다.
일반 싱글플레이는 `http://localhost:8060/`으로 실행한다.
기본 도시 출발점은 본편과 같은 강남 인도이며, 최대 네 명을 인도 방향으로 나눠 생성한다.

다른 장으로 서버를 시작할 때:

```sh
godot --headless --path . res://scenes/session/server.tscn -- --chapter=3
```

브라우저는 서버의 장을 받으며 로컬 URL이나 저장으로 장을 정하지 않는다.
네이티브 클라이언트도 사용할 수 있다:

```sh
godot --path . res://scenes/session/client.tscn
```

이전의 작은 연습장으로 서버를 시작할 때:

```sh
godot --headless --path . res://scenes/session/server.tscn -- --world=arena
```

클라이언트는 welcome의 월드 종류를 따르므로 같은 웹 주소를 사용한다.
종료는 각 터미널에서 Ctrl+C. 기본은 127.0.0.1:9080이며 외부 접속·초대 코드는 아직 없다.
서버와 웹의 welcome/스냅숏 형식이 함께 바뀌었으므로 이전 빌드의 탭은 새로고침한다.

## 구현

- `City.presentation_enabled`: 기본 true로 기존 싱글 동작을 유지한다. false이면 배치와
  충돌만 만들고 건물 그림·청크·물 셰이더·조명·렌더 조각을 만들지 않는다.
- `OverpassView.build(parent, presentation_enabled)`: 서버에도 고가 벽과 난간 충돌은
  만들되 표시 조각만 생략한다. 다른 호출은 기본 true로 기존처럼 동작한다.
- `session_bootstrap.gd`: 서버의 도시 생성, 월드 종류·장 전달, 도시 출발점,
  층 전송, 예측과 재실행의 도시 모드 선택을 담당한다.
- `session_motion.gd`: 1/60초 이동마다 `test_move`로 정적 벽을 검사한다. 충돌 후 남은
  이동을 벽 방향으로 최대 세 번 미끄러뜨린다. 예측 재실행에서도 같은 검사를 사용한다.
  클라이언트가 보낸 시간·이동 거리·좌표는 사용하지 않는다.
- `session_view.gd`: 도시 모드에서는 연습장 바닥을 그리지 않고 기존 ChaseCamera를
  자기 플레이어에 연결한다. 이름표는 투영과 지면 높이를 반영하며 카메라 적용 뒤 갱신한다.
- `scenes/session/client.tscn`, `server.tscn`: 기본 월드를 도시로 선택한다.

동적 차량·피격·밀림이 추가되면 정적 충돌 재실행만으로는 충분하지 않다.
그 결과와 충돌 대리체를 서버 기준으로 복제하는 후속 구현이 필요하다.

## 확인 기록

검증 로그와 브라우저 화면은 `output/web/city-multiplayer-proof/`에 저장한다.

2026-10-21, Godot 4.7.2, 로컬 loopback에서 확인했다.

- 기존 회귀 19종과 실제 WebSocket 네트워크 1종, 총 20종 PASS.
  별도 임시 도시 진단도 PASS (`verification.txt`, `tests/`, `diag.log`).
- 서버·두 클라이언트의 건물 배치 297개가 일치했다. 서버의 건물 표시 목록은 비어 있고
  물 셰이더도 생성되지 않았다. 네 명의 출발 위치 모두 정적 충돌 밖이었다.
- 달리기 후 서버·클라이언트 좌표 수렴, 건물 벽 차단, 고가 층 전송, 서버의 3장 설정 전달,
  이동 뒤 늦은 입장과 퇴장 정리를 확인했다. 이 진단의 각 참가자는 별도의 World2D를 썼다.
- 실제 웹 검증은 별도 임시 프로필의 Chrome 두 세션으로 실행했다. 각자 걷기·달리기를
  입력하고 두 화면을 차례로 활성화해 정지 좌표 수렴과 자기 카메라를 확인했다.
  최종 브라우저 로그와 서버 로그에 오류·경고 없음. 동시 종료 후 두 참가자 정리도 확인했다.
- 최종 웹 10초 표본: 양쪽 평균 33.33ms, p95 34.07/34.08ms,
  draw calls 2356/2309, 34ms 초과 19/28회. 약 30FPS이며 무끊김을 보장하지 않는다.
  `browser-logs.json`, `browser.log`, `client-1.png`, `client-2.png`에 기록했다.
- 기존 본편 3장 창 모드 180프레임과 전체 iso 스크린샷에서 SCRIPT ERROR·Invalid polygon 없음.
- Forward+ 본편 perf_probe 16초 전후:
  - 주행 평균 18.69ms/끊김 3회 → 16.82ms/2회.
  - 폭발 평균 23.81ms/끊김 8회 → 22.76ms/8회.
  - 변경 전에는 989.4ms 일시 정지 한 프레임이 포함됐다. 공유 컴퓨터에서 측정한 단일 표본이므로
    이 차이를 최적화 성과로 단정하지 않는다. 로그는 `before-perf.log`, `after-perf.log`다.
- 외부 인터넷·Safari/Firefox·모바일·도시 네 명 동시 장시간 플레이는 검증하지 않았다.
  초기 자동화의 오디오 자동재생 경고는 클릭 제스처를 준 최종 실행에서는 없었다.

## 이번에 확인한 함정

- 도시 그림 생성을 생략할 때 고가 벽·난간 충돌까지 생략하면 서버와 브라우저가 서로 다른
  지형을 걷는다. OverpassView의 물리와 표시만 나눠야 한다.
- 미확인 예측 입력이 없는데도 항상 위치 보정을 감쇠시키면 서버 위치를 불필요하게 뒤늦게
  따라간다. 이 경우 서버 위치를 바로 적용하도록 고쳤고 수렴·입퇴장 검증을 세 번 연속 통과했다.
- 서버 종료 중에는 MultiplayerAPI 참가자 목록과 실제 소켓 상태가 다를 수 있다.
  peer 연결 상태와 WebSocket STATE_OPEN을 확인한 뒤 보낸다.
- 참가자 사이의 직접 RPC는 쓰지 않아 SceneMultiplayer.server_relay를 끈다. 입퇴장·참가자 정보는
  서버 스냅숏으로 받는다. 불필요한 피어 간 종료 통지와 중계가 동시 종료 경합을 만들 수 있었다.
