# 20. 플레이어 등록부와 세션 역할

2026-10-21. [멀티플레이 설계](18_웹_2-4인_멀티플레이_설계.md) 및 [입력 분리](19_플레이어_입력_분리.md)의 다음 구현 단계다.
실제 네트워크 연결·도시 복제·서버용 AI 분리는 아직 구현하지 않았다.

## 이번에 분리한 책임

| 파일 | 책임 |
|---|---|
| `scripts/session/player_session.gd` | 참가자 ID, 현재 peer ID, 캐릭터·조종권·무기 참조 |
| `scripts/session/player_registry.gd` | 최대 4인, ID·peer·캐릭터 중복 방지, 연결 재매핑, 참가자 조회·제거 |
| `scripts/session/session_context.gd` | OFFLINE/SERVER/CLIENT 역할, 로컬 참가자 선택, 연결 소유자에 따른 입력 전달 |
| `scripts/session/session_actors.gd` | 참가자 캐릭터의 생성·해제, 역할별 물리/표시 설정, 클라이언트 위치 적용 |
| `scripts/session/session_bootstrap.gd`, `scenes/session/server.tscn`, `client.tscn` | 역할별 최소 실행 진입점 |
| `scripts/main.gd` | 기존 싱글 캐릭터·조종권·무기를 등록부에 연결하고 장면 종료 시 제거 |

Main.player/director/weapons는 기존 싱글 코드 호환용 별칭이다. 등록부의 로컬 참가자가 같은 객체를 가리킨다.
역할은 context 생성 시 정하며 headless 실행 여부로 권한을 판단하지 않는다. headless 테스트의 싱글은 계속 권한을 가진다.
Main은 새로운 OFFLINE context에서만 초기화한다. SERVER/CLIENT context를 주면 진단 오류를 출력하고 본편 세계를 생성하지 않는다.
기존 도시·AI·HUD를 클라이언트가 중복 실행하는 것을 막는 경계이며, Main을 완성된 전용 서버로 바꾼 것은 아니다.

## 역할별 동작

| 역할 | 게임 결과 계산 권한 | 로컬 입력 | 캐릭터 물리 | 캐릭터 표시 처리 |
|---|---|---|---|---|
| OFFLINE | 있음 | 선택한 참가자 한 명 | 실행 | 실행 |
| SERVER | 있음 | 없음 | 외부 명령으로 실행 | 매 프레임 표시 처리 끔 |
| CLIENT | 없음 | 선택한 참가자 한 명의 입력 수집 가능 | 실행하지 않음 | 수신 위치로 표시 |

클라이언트의 로컬 캐릭터도 이번 단계에서는 물리를 실행하지 않는다. 로컬 예측과 서버 보정은 다음 단계다.
CLIENT 컨테이너는 City·TrafficSystem·PoliceDispatcher·HUD·Director·PlayerWeapons를 생성하지 않는다.
SERVER 컨테이너도 아직 참가자 캐릭터만 만들며, 이후 서버 부트스트랩에서 도시 충돌·AI·전투 서비스를 연결해야 한다.

## 식별과 재접속

- `player_id`: 양의 정수. 방 안 참가자 식별자. 연결이 바뀌어도 유지한다.
- `peer_id`: 현재 연결 식별자. 0은 미연결/로컬 전용이며 실제 외부 입력 송신자로 인정하지 않는다.
- 같은 참가자 ID, 같은 양의 peer ID, 같은 캐릭터 노드의 중복 등록은 거부한다.
- 동시에 등록할 수 있는 참가자는 4명이다. 재접속 대기 슬롯도 등록부에 남겨 정원에 포함한다.
- `bind_peer(id, 0)`은 입력을 중립으로 만들고 이전 연결을 해제한다. 레코드 자체는 유지한다.
- 재접속 확인 뒤 `bind_peer(id, 새_peer)`를 호출하면 player_id는 그대로이고 이전 peer 입력은 거부한다.
- `remove(id)`로 완전히 퇴장한 ID는 같은 context 수명 동안 재사용하지 않는다. 새 방은 새 context를 만든다.
- 관심 영역 이탈을 참가자 퇴장으로 처리하지 않는다. NPC/차량 entity_id 등록부는 아직 별도 구현 전이다.

등록부는 레코드를 소유하고 씬은 노드를 소유한다. PlayerRegistry.remove는 노드를 해제하지 않는다.
SessionActors로 만든 캐릭터는 SessionActors.remove_player로 중립화·물리 정지·queue_free·등록 제거를 함께 수행한다.
SessionActors 밖에서 생성한 캐릭터의 제거는 그 씬 소유자가 처리해야 한다. Main은 장면 종료 때 자신이 등록한 참가자만 제거한다.
캐릭터가 외부에서 먼저 해제되더라도 GamePlayerSession.has_actor는 유효성을 검사한다.

## 서버 컨테이너 사용 예

```gdscript
var actors := SessionActors.new()
actors.session = GameSessionContext.new(GameSessionContext.Role.SERVER)
add_child(actors)
actors.spawn_player(10, 101, Vector2(100, 100))
actors.spawn_player(20, 102, Vector2(400, 100))

var command := PlayerInputCommand.new()
command.move_world = Vector2.RIGHT
actors.session.submit_from_peer(101, command) # 참가자 10만 제어
actors.session.action_from_peer(101, &"enter_exit")
```

단발 동작은 해당 캐릭터 control에 전달된다. 컨테이너는 Director/PlayerWeapons를 아직 만들지 않으므로
실제 탑승·발사를 하려면 이후 월드 서비스가 이 컴포넌트들을 생성·연결해야 한다.

submit_from_peer와 action_from_peer는 SERVER에서만 허용한다. 메서드 인수의 peer는 향후 수신 어댑터가
실제 연결에서 얻은 ID를 전달해야 한다. 클라이언트 메시지에 적힌 peer/player_id를 그대로 넘기면 안 된다.
현재 검사는 연결-참가자 매핑이며 인증·재접속 토큰·RPC 권한 검증을 대신하지 않는다.

## 클라이언트 컨테이너 사용 예

```gdscript
var actors := SessionActors.new()
actors.session = GameSessionContext.new(GameSessionContext.Role.CLIENT)
add_child(actors)
# 아래 호출은 향후 신뢰할 서버 연결의 초기 상태 수신 처리에서 수행한다.
actors.spawn_player(10, 0, Vector2(100, 100))
actors.session.set_local_player(10)
actors.apply_player_state(10, Vector2(120, 100), Vector2(110, 0), 0.0, 0)
```

spawn/apply의 좌표는 월드 좌표다. 컨테이너가 이동한 경우에도 같은 좌표를 적용한다.
현재 apply_player_state는 위치·속도·방향·층만 즉시 적용한다. 유효하지 않은 수치·층과 SERVER에서의 호출을 거부한다.
서버 틱/epoch/버전·이벤트 순서, 보간, 애니메이션 시각, 체력 등 전체 상태는 다음 동기화 단계에서 추가한다.
등록부에 없는 local_player_id는 선택할 수 없고, 서버는 로컬 참가자를 선택할 수 없다.

session 객체와 Player.control 객체는 참가자 노드가 살아 있는 동안 교체하지 않는다.
연결 변경에는 bind_peer, 입력 출처 변경에는 control.use_external/use_local을 사용한다.

## 별도 진입점 실행

```sh
godot --headless --path . res://scenes/session/server.tscn
godot --path . res://scenes/session/client.tscn
```

두 씬은 역할과 빈 참가자 컨테이너만 준비한다. 아직 네트워크를 열지 않으며 클라이언트 창도 빈 화면이다.
기존 게임 실행은 기본 main_scene을 사용한다. 전용 서버/클라이언트 씬에 도시·통신을 연결하는 것은 다음 단계다.

## 확인 방법

```sh
godot --headless --path . --import
godot --headless --fixed-fps 60 --path . res://tests/session_context_test.tscn
```

새 검증은 정원·중복 ID/연결/캐릭터, peer 재매핑, 해제된 노드 조회, 두 서버 캐릭터의 독립 입력,
클라이언트의 물리 중복 실행 방지, 월드 좌표 적용, 퇴장과 context 수명, 싱글 Main 별칭 연결을 검사한다.

이번 단계는 두 브라우저가 접속하는 멀티플레이 완성이 아니다. 다음 단계에서 SessionActors를 만들 서버/클라이언트
부트스트랩, 실제 연결, 초기 상태 전송과 입력 시퀀스/만료/중복 방지를 추가한다.
